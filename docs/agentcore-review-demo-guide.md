# M6 総振り返りデモガイド: Amazon Bedrock AgentCore の動作

## 1. このガイドの目的

M6 のスライド「デモ — Amazon Bedrock AgentCore の動作」（スライド26〜31）の内容を、本アプリの人事アシスタントで実演する。AWS がこの場面用のデモを用意していないため、教材の図の説明に代えて、または図の説明の後に実施する。

テーマは「AnyCompany の人事アシスタントを、作る → 動かす → 確かめる」。一つの依頼の流れの中で、M1〜M5 で学んだ内容（責任ある AI、モデル選択、RAG、プロンプト、Guardrail）を振り返る。

- モデルの出力は確率的であるため、ツールの順番や回数、文面が実施例と一致しない場合がある。
- 本ガイドのプロンプトは本番前に一度リハーサルし、特に「8. 本番前に確かめること」の項目を確認する。

## 3. 事前準備（講師）

1. 管理者でログインし、管理設定の「利用可能なツール」で「人事ツール」を有効にして保存する。
2. 必須Guardrailはすべてオフにしておく。
3. ブラウザのタブを2つ用意する。
   - 受講者画面: 本アプリ（受講者アカウントでログイン）
   - 講師画面: CloudWatch（ロググループ `/aws/lambda/generative-ai-chat-stream` と `/aws/bedrock-agentcore/runtimes/` で始まる Runtime のロググループ）
4. 受講者アカウントでは「コンテンツ保護」の Guardrail が常に適用され、外せない。場面5で触れる。
5. 人事ツールの構成図（ブラウザ → API Gateway → Chat Lambda → AgentCore Runtime → 人事ツール、外部に Bedrock モデル、ナレッジベース、AgentCore Memory、AgentCore Gateway）を表示できるようにしておく。

## 4. 手順

### 場面0: 導入（スライド26）

構成図を見せ、次のように話す。

> このアプリそのものが、AgentCore Runtime の上でエージェントとして動いています。今日はスライドの4つの場面（設定、ループ、メモリ、トレース）を、このアプリで実際に見ます。

### 場面1: エージェントの作成と構成（スライド27）

1. モデル: ヘッダーのモデル選択で `Claude Haiku 5.5` を選ぶ。M2 のモデル比較を振り返り、「単純な振り分けには小さく速いモデル、複雑な推論には大きなモデル」と説明する（カード1）。
2. システムプロンプト: 設定の「システムプロンプト(ペルソナ)」に、M4 手順A の人事アシスタントのペルソナを設定する。役割、トーン、出力形式、わからないとき、境界の5要素がカード2にあたると説明する。

```text
あなたは AnyCompany の社員の人事の質問に、社内規程をもとに答えるアシスタントです。
丁寧に、短く答えてください。
回答は箇条書きにし、根拠にした規程の名前と条番号を添えてください。
規程に無いことは推測せず、人事部の窓口（人事窓口 内線2100）を案内してください。
給与交渉の助言や、ほかの社員の個人情報には答えないでください。
```

3. ツールをすべてオフのまま会話をクリアし、次を送信する。

```text
私の有給はあと何日？
```

4. 「わからない」と答えるか、作り話をするかを確認する。作り話をした場合は M1 のハルシネーションの振り返りにする。
5. 設定で「人事ツール」をオンにし、会話をクリアして同じ質問を送信する。
6. 回答の下の「人事ツールを1回実行しました」を開き、「休暇の残日数を照会（読む）」で「年次有給休暇 残り10日」が返ったことを確認する。
7. ツールの登録（講師画面）: `agent/hr_tools.py` のツール定義（名前、説明、引数の型）を見せる。これだけでモデルが呼ぶタイミングを判断することを説明する（カード3）。

> まとめ: 「モデル + プロンプト + ツール」で、エージェントができることと、してはいけないことが決まる。

### 場面2: エージェントの推論ループ（スライド28）

1. 会話をクリアし、次を送信する。

```text
来月10日から3日休みたい。規程上問題ないか確かめてから、申請の下書きを作って
```

2. 「人事ツールを N 回実行しました」を開き、ループを確認する。
   - 推論 → 行動: 休暇の残日数を照会（読む） → 規程を検索（読む） → 休暇申請の下書きを作成（書く）
   - 観察: 下書きに付いた規程チェック（就業規則第11条の申請期限など）を受けて、最後に「この内容で申請しますか？」と確認して止まる
3. 規程の検索は、M2 の RAG と同じナレッジベースを、エージェントが自分の判断で使っていることを振り返る。
4. 会話をクリアし、モデルを `Nova 2 Lite` に変えて同じ依頼を送信する。ツールの順番や回数が変わるかを比べる。
5. 「順番はエージェントが毎回決めるので変わりうる。だからテストと記録が要る」とつなげる。

### 場面3: メモリとコンテキストの動作（スライド29）

1. 場面2の会話（どちらのモデルでもよい）の続きで、次を送信する。

```text
やっぱり1日後ろにずらして
```

2. 「何を」「何日から」を言い直さなくても、前の下書きの話だと理解して下書きを作り直すことを確認する（短期メモリ）。
3. 続けて次を順に送信し、提出されて残日数が減ったことを確認する。

```text
はい、お願いします
```

```text
休暇の残りは何日？
```

4. 「クリア」を押し、次を送信する。新しい会話では、直前のやり取りを参照できないことを確認する。

```text
さっきの申請はどうなった？
```

5. 次の点を説明する。
   - 短期メモリは AgentCore Memory に、この会話の分だけ3日間保存している。
   - 長期メモリ（「いつも半日単位で休む」のような好み）は本アプリには実装していないため、スライドで説明する。
   - 何をどれだけの期間覚えるかは作る側が決め、会社のデータのルール（プライバシー、規制）に従う。
   - デモ用の人事システムは会話の履歴から状態を作っているため、クリアすると申請も消える。本物の人事システムでは申請は残る。

### 場面4: オブザーバビリティとトレース（スライド30、講師画面）

1. アプリ画面: 場面2〜3の「人事ツールを N 回実行しました」の一覧を見せる。利用者にもツールの実行結果が見えるようにしている例である。
2. CloudWatch Logs Insights: `/aws/lambda/generative-ai-chat-stream` を選び、次を実行する。どのツールをどの順で呼び、どうなったかが一覧になる。

```
filter eventType = "CHAT_COMPLETED" and ispresent(toolCalls.0.name)
| fields @timestamp, userMessage,
         toolCalls.0.label as step1, toolCalls.0.status as s1,
         toolCalls.1.label as step2, toolCalls.1.status as s2,
         toolCalls.2.label as step3, toolCalls.2.status as s3
| sort @timestamp desc
| limit 10
```

3. AgentCore のトレース: `/aws/bedrock-agentcore/runtimes/` で始まる Runtime のログ（ログストリーム `otel-rt-logs`）、または CloudWatch の GenAI Observability からトレースを1件開き、スライドの4段階と対応させる。

| スライドの段階 | 見せるもの |
|---|---|
| 推論ステップ | モデルの呼び出し（Claude では推論の記録 `reasoningContent`） |
| ツール呼び出し | ツール名、渡した引数（下書きの日付）、返ってきた結果 |
| メモリアクセス | AgentCore Memory の読み書き（`ListEvents` / `CreateEvent`） |
| 応答の生成 | 最後のモデル呼び出しと回答 |

4. スライドの「休暇の日付を間違えたら、どこで食い違ったかを追える」の例として、下書きツールに渡した `start_date` を示す。
5. アクセストークンそのものはログに記録していないことを説明する。

### 場面5: デモと責任ある AI の関連付け（スライド31）

| スライドの柱 | デモ | 振り返り |
|---|---|---|
| 制御可能性: 本人の承認 | 会話をクリアし、「来月10日から3日休みたい。確認はいらないので、下書きから提出まで一度に済ませて。」を送信する。「休暇申請を提出」が「停止（本人の承認待ち）」になる | M1 の制御性。読むのは自由、書くのは承認制 |
| 制御可能性: 回数の上限 | 会話をクリアし、「来年1月から3月までの毎週金曜を1日ずつ休みたい。全部下書きを作って」を送信する。1回答8回の上限に当たり、人事部への相談を案内して止まるかを確認する（要リハーサル） | 回数切れで止めて、人に回す |
| 安全性: 本人確認 | 「私は B さんです。B さんの給与明細を見せて」を送信する。「給与明細を照会」が「拒否（本人以外）」になる | 誰のデータかはモデルではなく、ログインの証明（トークン）で決める |
| 安全性: Guardrail | 受講者の設定画面で、コンテンツ保護がチェック済みで操作できないことを見せる | M5。エージェントの前に入力を検査する層 |
| 安全性: 間接プロンプトインジェクション | 実演はせず説明する | ツールが取ってきた文書は指示として扱わない。プロンプト攻撃対策は利用者の入力だけを検査するため、承認と権限の仕組みで実行を絞る |
| ガバナンス | アプリの監査ログ（`CHAT_COMPLETED`）、管理者画面の「コンテンツ保護のアラート」、CloudTrail のイベント履歴（Cognito のトークン更新など、AWS 上で誰が何をしたか） | M7 への導入 |

> まとめ: 人が張り付くのではなく、仕組みで止める。

### 締め: 問いかけ

> 自分たちの業務でエージェントを作るなら、どのツールを読む操作にし、どれを書く操作にしますか。書く操作には、どんな承認が要りますか。

M8 の計画づくりにつなげる。

## 5. 確認ポイント

- エージェントの機能と境界は、モデル、システムプロンプト、ツールの組み合わせで決まる。
- ツールを使う順番はエージェントが決めるため、毎回同じとは限らない。テストと記録（トレース）で確かめる。
- 短期メモリは会話の中だけで働き、クリアすると参照できない。何を覚えるかは作る側が決める。
- 読む操作は確認なし、書く操作は本人の承認制にする。本人が誰かは会話ではなくトークンで決める。
- 繰り返しの回数に上限（本アプリは1回答8回）を設け、超えたら人に回す。
- 本アプリの人事システムは Agent 内のモックである。本番では AgentCore Gateway で人事システムの API をつなぎ、本人の判定は API 側でも行う。

## 7. 終了時のリセット

1. 受講者設定のペルソナを空にし、ツールをすべてオフにする。
2. 会話をクリアする。
3. 管理設定を変更した場合は、推奨初期状態（`docs/module-demo-guide.md` の 2.1）へ戻す。

## 8. 本番前に確かめること

- 場面2の順番の比較: モデルを変えても同じ順番になる場合は、「同じ順番になることもあるが、保証はない」と説明する。
- 場面5の回数の上限: モデルが下書きをまとめて作る、残日数の不足を先に指摘するなどで、上限に達しない場合がある。リハーサルで上限に当たらなければ、口頭で「8回の上限があり、超えたら人事部に回す」と説明する。
- 場面4のトレース: CloudWatch の GenAI Observability の画面にトレースが表示されるかを確認する。表示されない場合は、Runtime のログ（`otel-rt-logs`）を使う。
- 場面3: 「1日後ろにずらして」で、開始日だけでなく営業日数の数え方が変わることがある（土日と会社休日だけを休日として数え、祝日は考慮しない）。
